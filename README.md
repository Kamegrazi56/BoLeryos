# BoLeryos

Bot d'automatisation pour Aleryos, destiné aux **tests de protection anti-bot réalisés avec l'éditeur** (GEEKOS NEXUS). Il tourne dans Docker et se pilote depuis une interface web.

> Le règlement du jeu (§12) interdit les bots sur les comptes de joueurs. Ce projet ne doit être utilisé que dans le cadre de l'accord avec l'éditeur, de préférence avec un compte de test dédié.

> Plan de développement, décisions prises et feuille de route : [`docs/PLAN.md`](docs/PLAN.md).

Interface au style inspiré d'Aleryos (espace profond, panneaux translucides, accents cyan et violet).

| Page | Rôle |

| `/ecran` **Écran** | Vue en direct du navigateur du bot, contrôle manuel (jouer soi-même dans la même vue), choix d'univers et exploration de la structure du site. |

### Navigateur complet (page Écran)

Dans l'image Docker, le Chromium du bot tourne avec sa **vraie fenêtre** (onglets, barre d'adresse) sur un écran virtuel, affiché dans la page **Écran** par **noVNC** : on navigue et on joue comme dans un vrai navigateur, au clavier et à la souris, comme avec le conteneur « Chromium » de linuxserver. C'est le même navigateur que celui qu'utilise le bot.

- Le navigateur occupe **toute la page sous le bandeau du haut**. Dans ce bandeau : « Contrôle manuel », « Plein écran », « Outils & journal » (panneau escamotable : page affichée, univers, exploration de la structure, journal, déconnexion).
- **Regarder** : par défaut, la vue est en lecture seule (le bot peut agir). La **molette fait toujours défiler la page du jeu**, même sans contrôle manuel ; clics et clavier restent bloqués.
- **Contrôle manuel** : cochez la case pour cliquer, taper, faire défiler, utiliser la barre d'adresse ou les onglets ; le bot se met en pause tant qu'elle est cochée (et la décoche tout seul quand plus aucun écran n'est ouvert).
- **Plein écran** : bouton au-dessus de la vue (Échap pour sortir). L'écran virtuel prend toujours la taille de la zone d'affichage : image nette, sans bandes vides.
- Rien de plus à exposer : le serveur VNC n'écoute que dans le conteneur, la page passe par le port du bot (7654) et sa vérification d'origine ; la protection `ui_user` / `ui_password` s'applique aussi.
- Le bot travaille dans le premier onglet : un onglet ouvert à la main n'est pas vu par le bot.
- Toute personne qui accède à l'interface peut agir sur le compte du jeu : protégez-la (`ui_user` / `ui_password`).

### Vue par images (hors Docker)

Sans écran virtuel (tests, développement), la page Écran affiche un flux d'images poussé par Chrome (CDP `Page.startScreencast`) avec un contrôle manuel simplifié ; les mouvements de souris en attente y sont fusionnés pour qu'un clic parte tout de suite.

### Choix de l'univers

Après la connexion, la page « Choisissez votre univers » du jeu est lue par le bot : un bouton par univers apparaît au-dessus de l'écran, et un clic le fait entrer (avec les délais humains). La détection repose pour l'instant sur le seul libellé observé (« Reprendre la partie ») et sur une structure supposée d'après une capture d'écran : à confirmer avec l'export ci-dessous. En attendant, le contrôle manuel permet de cliquer soi-même.

### Exploration de la structure du site

Le panneau « Exploration de la structure du site » (désactivé par défaut) enregistre, pendant que vous naviguez, la structure des pages (balises, attributs, tous les textes visibles : niveaux, coûts, durées…), les chemins d'API et la **forme** des réponses JSON et des messages WebSocket. Il exporte un fichier `boleryos-structure.json`.

- Conservés : chemins (identifiants remplacés par `{id}`), noms de paramètres, **noms** d'en-têtes, de cookies et de clés de stockage, types des valeurs, courts libellés alphabétiques (ex. `open`).
- Jamais conservés : valeurs de cookies, d'en-têtes et de stockage, valeurs de paramètres d'URL, mots de passe et saisies, e-mails, jetons, identifiants. Des tests le vérifient.
- Les textes visibles à l'écran (titres, boutons, pseudo) et les courts libellés peuvent contenir des informations de jeu : relisez le fichier avant de le partager. Ne le commitez pas dans un dépôt public.

## Instances : plusieurs serveurs en même temps

Une **instance** est un bot sur un serveur du jeu : elle a son univers, ses réglages, ses relevés et son planning, et se démarre, s'arrête, se crée et se supprime sans toucher aux autres. Le **compte** (identifiant, mot de passe, cookies de connexion) est commun à toutes les instances.

1. Sur l'**Accueil**, saisir l'identifiant et le mot de passe (**Se connecter**). Aucun univers n'est demandé.
2. Le bot se connecte, **relève seul la liste des serveurs** du compte et **reste sur la page de choix des univers** sans en ouvrir aucun (le bouton **Relire mes serveurs** relance la lecture). La lecture se refait aussi au redémarrage du conteneur quand des identifiants sont enregistrés et qu'aucune instance ne tourne (`AUTOSTART=0` pour l'éviter). Si des instances tournent déjà, aucune session de connexion n'est ouverte (mémoire) : le bot lit la liste dès qu'une instance affiche la page des serveurs, même si la connexion a été faite à la main depuis l'écran (sans identifiants enregistrés) ; le bouton **Relire mes serveurs** fait la même chose à la demande.
3. **Créer une instance** sur l'un des serveurs listés, puis **Démarrer**. Le jeu n'accepte qu'une session par compte et par serveur : une seule instance par serveur. Le nombre d'instances est limité (`MAX_INSTANCES`, 5 par défaut).

- **Sélecteur d'instance** dans l'en-tête (dès qu'il y en a plusieurs) : Écran, Réglages et Suivi montrent l'instance choisie, **dans cet onglet** (deux onglets peuvent donc montrer deux instances). Une instance arrêtée est signalée par une bannière avec un bouton **Démarrer**.
- **Un seul Chromium** pour tout le monde, avec **un contexte par instance** (session de jeu indépendante) : environ 410 Mo pour le navigateur puis environ 105 Mo par instance supplémentaire (mesuré sur une page de test ; la mémoire réelle est affichée sur l'Accueil).
- **Écran** : toutes les fenêtres partagent le même écran virtuel ; celle de l'instance qu'on regarde est remontée devant. Deux onglets Écran sur deux instances différentes montrent donc la même fenêtre, la dernière remontée.
- **Redémarrage du conteneur** : les instances qui tournaient reprennent leur connexion (une après l'autre, à quelques secondes d'écart), avec le bot sur **OFF** : rien ne se lance tant qu'on ne l'a pas remis sur ON (`AUTOSTART=0` pour désactiver la reprise).
- **Suppression** : le dossier de l'instance est déplacé dans `/data/instances/.corbeille/`, jamais effacé.
- Adresses : `/api/i/<instance>/…` et `/ws/i/<instance>/…` visent une instance ; sans préfixe, c'est la première. `compte` désigne la session de connexion (identifiants et liste des serveurs, sans instance). La gestion est sous `/api/instances`.
- Disposition de `/data` : `account.json`, `account.key`, `browser-state.json`, `discord.json` et `instances.json` à la racine ; `instances/<id>/` pour tout ce qui est propre à un serveur.

## Piloter le bot par Discord (Réglages › Discord)

Le bot peut recevoir des ordres depuis Discord, par des commandes « slash ». C'est **votre** bot Discord (vous le créez, vous le gardez) ; le bot de jeu s'y connecte de lui-même, **aucun port à ouvrir**.

**Mise en place** (une seule fois) :
1. Portail développeurs de Discord : créer une application, y ajouter un **bot**, copier son **jeton**.
2. Inviter le bot sur votre serveur privé avec les portées `bot` et `applications.commands` (aucun droit particulier, aucune « intention » privilégiée).
3. Réglages › **Discord** : coller le jeton, cocher **Pilotage par Discord activé**, **Enregistrer**. L'état de la connexion s'affiche en haut du panneau. **Le jeton est le seul réglage obligatoire.**

**Ce que le bot lit tout seul chez Discord** : les serveurs où il est invité (les commandes s'y installent, y compris sur un serveur où on l'invite plus tard) et son propriétaire. Si le bot n'est invité nulle part, ou sans la portée `applications.commands`, le panneau le dit.

**Qui peut commander** : seulement le propriétaire de l'application Discord (ou les membres de son équipe, si l'application appartient à une équipe), depuis un serveur. Toute autre personne reçoit « Commande réservée ». Les réponses ne sont visibles que de la personne qui commande.

| Commande | Effet |
|---|---|
| `/bot statut` | État de toutes les instances : connexion, bot ON/OFF, activité |
| `/bot demarrer [instance]` | Bot sur **ON** (toutes les instances démarrées, ou celle nommée) |
| `/bot arreter [instance]` | Bot sur **OFF** (le passage en cours se termine) ; sans nom d'instance, demande confirmation |
| `/instance liste` · `/instance statut <instance>` | Liste des instances ; détail d'une instance (fonctionnalités actives comprises) |
| `/instance demarrer <instance>` · `/instance arreter <instance>` | Démarre ou arrête la session d'une instance ; l'arrêt demande confirmation |
| `/fonction activer\|desactiver <fonction> [instance]` | Interrupteur d'une fonctionnalité (le bot doit être sur ON pour qu'elle tourne) |
| `/fonction statut [instance]` | Fonctionnalités activées (règle du minuteur, dernier passage et son résultat) et noms de celles qui sont éteintes |
| `/fonction lancer <fonction> [instance]` | Fait passer une fonctionnalité **activée** au prochain tour, sans attendre son minuteur (refusé si elle est éteinte ; si le bot est sur OFF ou hors planning, le message le dit) |
| `/prochain [instance]` | État du bot, du planning, et prochain passage de chaque fonctionnalité activée (sur OFF : aucun minuteur n'est annoncé) |
| `/flottes [instance] [actualiser]` | Flottes en vol du dernier relevé des Capteurs (hors flottes du bot, déjà arrivées retirées) et retours programmés. `actualiser` refait d'abord le relevé dans le jeu (lecture seule) |
| `/planetes [instance] [actualiser]` | Planètes du dernier scan avec leurs stocks de Fer, Cristal et Éther. `actualiser` refait d'abord le scan |
| `/pause <minutes> [instance]` | Bot sur **OFF** pendant 1 à 720 minutes, puis de nouveau sur ON tout seul (heure de reprise indiquée). Un `/bot demarrer` ou `/bot arreter` donné entre-temps annule la pause ; sans effet si le bot est déjà sur OFF. La pause ne survit pas à un redémarrage du conteneur (le bot reste alors sur OFF) |
| `/connexion [instance]` | Relance la connexion automatique (comme « Relancer la connexion » de l'interface) ; refusé s'il n'y a aucun identifiant en mémoire |
| `/scan [instance]` | Relit dans le jeu ce dont les fonctionnalités **activées** ont besoin, l'une après l'autre : planètes (toujours), modèles de vaisseaux, inventaire (bâtiments, recherches, population), effectifs de composants, Piliers, relevé des Explorations, des Fouilles, du Piratage (si une planète de départ est choisie), flottes en vol. Si le bot est en plein passage, chaque lecture attend son tour (jusqu'à 1 min). Réponse : ✅ ou ❌ par lecture. Plusieurs minutes possibles : Discord n'accepte de répondre que pendant 15 min |
| `/journal [instance]` | Derniers événements |

**Panneau de boutons** (sans taper de `/`) : dans Réglages › Discord, renseignez l'**identifiant du salon** (Discord en mode développeur › clic droit sur le salon › Copier l'identifiant) puis **Enregistrer**. Le bot y publie **un seul message** avec :
- un menu **Instance** (« Toutes les instances » ou l'une d'elles) et un menu **Fonctionnalité** ; le choix reste inscrit dans le message ;
- lecture : **État**, **Prochain passage**, **Flottes**, **Planètes**, **Journal** (sous Flottes et Planètes, un bouton **Actualiser dans le jeu** refait la lecture) ; **État** d'une instance propose aussi **Démarrer / Arrêter la session** ;
- action : **Bot ON**, **Bot OFF**, **Pause…** (menu de durée : 15 min à 12 h), **Reconnecter**, **Relire le jeu** ; **Activer**, **Désactiver**, **Lancer** (sur la fonctionnalité choisie), **Fonctions** (état) ;
- **Actualiser le panneau** : relit la liste des instances (une instance créée ou supprimée depuis n'apparaît qu'après).

Les boutons passent par les mêmes commandes que les `/` : mêmes règles, mêmes **confirmations** (Bot OFF sur toutes les instances, arrêt d'une session), même ligne dans le journal. Les réponses ne sont visibles que de vous. **Réservé au propriétaire** et **au salon choisi** : un autre utilisateur, ou un clic venu d'un autre salon, est refusé. Les commandes `/` ne changent pas et marchent partout.

Le panneau **survit aux redémarrages** : l'identifiant du message est gardé dans `/data/discord.json` (`panel_message`) et les boutons n'ont pas besoin de mémoire. À chaque connexion, le bot **met à jour le même message** ; si l'identifiant est perdu, il reprend le panneau déjà présent dans les 50 derniers messages du salon au lieu d'en publier un second ; si vous supprimez le message, il en republie un. Changer de salon publie un nouveau panneau dans le nouveau salon (l'ancien message reste, à supprimer à la main). Il faut que le bot ait le droit de **voir le salon, d'y écrire et de lire l'historique** ; sinon l'état Discord du panneau de réglages affiche « Panneau non publié ». Laisser le salon vide : pas de panneau, tout clic « pn: » est refusé.

- Le nom d'une instance se tape en entier ou en partie (la saisie propose la liste) ; une instance arrêtée est refusée par toutes ces commandes (sauf `/instance`) avec un message clair. Sans nom, les commandes de lecture et d'action visent toutes les instances démarrées.
- **Confirmation** : par défaut, arrêter tout (`/bot arreter` sans instance) ou arrêter une instance demande de cliquer sur **Confirmer**. La case « Demander une confirmation avant d'arrêter » la retire.
- Chaque ordre exécuté laisse une ligne dans le journal de l'instance concernée (« … par une commande Discord »).
- **Bilan de fin de journée** : quand le bot **suit le planning** et s'arrête après la **dernière plage du jour** (le même moment que la récupération des missions), il envoie un **message privé** Discord à chaque propriétaire de l'application : une ligne par fonctionnalité (nombre de passages, échecs, dernier résultat) et les missions récupérées. Aucun réglage : il part si le pilotage Discord est actif et connecté, et s'il y a eu au moins un passage dans la journée. Le bilan est tenu **en mémoire** (un redémarrage du conteneur le remet à zéro) ; il n'est pas envoyé si une fonctionnalité « hors planning » garde le jeu ouvert, ni si les messages privés des membres du serveur sont fermés dans Discord (le journal le dit : « Bilan de fin de journée non envoyé »). Un message par instance.
- Stockage : `/data/discord.json` (droits 0600). Le jeton n'est jamais renvoyé par l'interface (seulement ses 4 derniers caractères), jamais écrit dans le journal ni exporté ; **Oublier le jeton** le supprime et coupe le pilotage. API : `GET/PUT /api/discord` (jeton, activation, confirmation, `panel_channel`), `DELETE /api/discord/token` (réglages communs à toutes les instances).
- Les tests utilisent un faux Discord local (`tests/mock_discord.py`, `tests/test_discord_panel.py` pour le panneau) : la validation finale se fait avec un vrai jeton sur un vrai serveur Discord (affichage des menus et du choix mémorisé compris).

## Connexion automatique et scan des planètes

Le bot ne lance **aucune action de jeu** : constructions, recherches, production, expéditions, espionnage, attaques, priorités, horaires, sauvegarde des réglages d'automatisation et alertes ont été supprimés pour repartir de zéro. Il se connecte, entre dans l'univers, reste connecté et lit la liste des planètes.

La connexion se fait **uniquement depuis la page Accueil** : saisissez l'identifiant et le mot de passe, puis **« Se connecter »** ; le bot se connecte **tout seul**, lit vos serveurs et, dans chaque instance, entre dans l'univers de l'instance et **reste connecté** (il se reconnecte si la session expire). **Réglages › Compte et univers** ne sert plus à se connecter : on y règle le délai entre clics et le moteur de lecture (l'univers est celui de l'instance, choisi sur l'Accueil). Tant qu'aucun univers n'est choisi, le bot reste sur la page des serveurs sans rien signaler dans le suivi. « Oublier » (Accueil) ou « Se déconnecter » (page Écran) arrête la connexion automatique. La session du navigateur est conservée dans le volume `/data` : un redémarrage du conteneur ne déconnecte pas.

| Écran du site | Ce que fait le bot |
|---|---|
| Page de connexion | Se connecte avec les identifiants mémorisés. |
| Choix de l'univers | Entre dans l'univers choisi (cliquer sur un bouton d'univers le mémorise aussi). |
| Déjà dans une partie | Saute la connexion et le choix de l'univers. |
| Session expirée | Se reconnecte tout seul. |
| Fenêtre « Journal de développement » | La ferme à tout moment (avant chaque clic ou saisie, et par la veille de fond toutes les secondes). |
| Annonce « Votre empire vous accompagne sur Steam » | La ferme aussi avant chaque clic ou saisie : elle apparaît à chaque chargement de page et empêchait d'ouvrir des fenêtres du jeu (Piliers, modèles). |
| Annonce « Vos packs sont arrivés à leur terme » | La ferme avec sa croix (jamais le bouton « Réactiver mes packs ») : tant qu'elle est ouverte, elle bloque les lectures et les clics. Si elle surgit juste APRÈS un clic sur « Modèles » (vu sur la production le 22/11 : relevé des modèles Piliers/Flotte en échec), le bot la ferme pendant l'attente de la fenêtre des modèles puis clique à nouveau (3 essais). |
| Toute autre annonce du jeu (ex. « Rattrapage galactique », relevée sur le vrai jeu le 22/11) | Fermée automatiquement **à tout moment** (avant chaque clic ou saisie, et par une veille de fond qui vérifie **toutes les secondes**, même quand le bot attend ou lit), sans qu'il faille la prévoir : le bot clique **uniquement** sur la croix « Fermer la transmission » (jamais sur « Lancer le rattrapage », « Réactiver… » ou « Réduire »). Plusieurs annonces empilées sont fermées l'une après l'autre ; le journal indique le titre de chacune. Les fenêtres que le bot ouvre lui-même (Piliers, Espionnage, modèles, confirmations) n'ont pas cette croix : il ne les ferme jamais. Une fenêtre d'un autre type, sans cette croix, reste à ajouter à la main dans `app/interruptions.py`. |

**Scans gardés d'un démarrage à l'autre :** la **liste des planètes** et les **modèles de vaisseaux** sont enregistrés dans `/data/scans.json` avec leur date. Au démarrage ou à une reconnexion, le bot ne les relit **que s'ils ont plus de 24 h** ; sinon il les reprend tels quels et l'écrit au journal (« lecture d'il y a 3 h gardée, pas de nouveau scan »). L'**inventaire** (Empire › Inventaire) suit la même règle avec **1 h**, et seulement si ses planètes sont celles du scan. Ces données ne servent qu'au même **univers et au même compte** : changer l'un ou l'autre les écarte et déclenche une nouvelle lecture (le nom du compte n'est pas écrit dans le fichier, seulement une empreinte). Les boutons **« Scanner »** / **« Relever »** et la commande Discord `/scan` relisent toujours le jeu, et les stocks de l'Accueil restent ceux du dernier scan. Les **Piliers** et les **modèles d'exploration** sont encore relus à chaque connexion. Non vérifié sur le vrai jeu.

**Scan des planètes :** une fois par connexion, dès que le bot est dans la partie, il ouvre la liste des planètes du jeu, lit nom, coordonnées et stocks (Fer, Cristal, Éther), puis la referme. Le bouton **« Scanner les planètes »** (Réglages) la relance à la demande ; le résultat s'affiche aussi sur l'Accueil.

**Lectures de démarrage :** après le scan des planètes, le bot lit aussi tout seul, une fois par connexion et dans cet ordre : les **modèles de vaisseaux** (Chantier spatial), l'**état des Piliers**, les **effectifs** (Empire › Inventaire : population, niveaux des bâtiments) et les **modèles d'exploration Piliers et Flotte** (Opérations). Ces données servent aux fonctionnalités et aux tableaux des Réglages : elles sont donc présentes dès le lancement de l'instance, sans clic. Chaque lecture est tentée 3 fois au plus par connexion ; une lecture qui échoue est signalée dans les événements et peut être relancée par son bouton. Les brèches de chaque planète restent relevées une fois par jour, au premier passage des explorations.

**Garde-fous :** si le site **refuse** les identifiants, le bot n'essaie qu'**une fois** (risque de blocage du compte) et l'indique ; si la connexion n'aboutit pas (contrôle anti-bot ?), 3 essais espacés (1 min, 5 min) puis il demande de se connecter à la main et **reprend seul** dès que le site est connecté ; le contrôle manuel le met en pause.

**Identifiants :** enregistrés par le bot dans le volume `/data` (décision D1 « B », demandée le 05/11/2026) : l'identifiant dans `account.json`, le mot de passe **chiffré** (Fernet) avec une clé aléatoire gardée à côté dans `account.key` (droits 0600). La clé protège contre une lecture du seul fichier, pas contre une copie de tout le dossier : utilisez un compte de test et protégez l'interface (`UI_USER` / `UI_PASSWORD`). Jamais dans le journal, ni dans les réglages exportés ; le mot de passe n'est jamais renvoyé par l'API (le champ reste vide et indique « enregistré »). Au redémarrage ils sont relus mais le bot **ne se connecte pas seul** : cliquez sur « Se connecter » (Accueil), mot de passe laissé vide. « Oublier le compte » efface les deux fichiers. Sans volume `/data`, ils restent en mémoire seulement.


**Préférences :** univers choisi et délai de connexion sont enregistrés dans le volume Docker `boleryos-data` (`preferences.json` de l'instance, non secret ; l'ancien `automation.json` est repris au premier démarrage).

**Organisation de `/data` :** le **compte** du joueur (`account.json`, `account.key`, `browser-state.json`) reste à la racine ; tout ce qui est propre à un serveur de jeu (réglages, objectifs, relevés, planning, univers choisi) est dans le dossier de son **instance**, `/data/instances/<identifiant>/` (l'identifiant vient de l'univers déjà choisi, par exemple `asterion`, sinon `principale`). Sur un **volume neuf**, la liste des instances démarre **vide** : aucune instance « Principale » n'est créée, on en ajoute depuis l'Accueil en choisissant un serveur. Au premier démarrage après la mise à jour d'un volume déjà utilisé, les anciens fichiers à plat sont **copiés** dans le dossier d'une instance reprise (jamais par-dessus des fichiers déjà présents) ; les originaux restent à la racine, inutilisés, et on peut les supprimer à la main une fois la mise à jour validée. Les chemins `/data/<fichier>.json` cités plus bas sont à lire dans le dossier de l'instance.

**Données conservées entre deux mises à jour :** tout reste dans le volume Docker `boleryos-data` monté sur `/data`. Dans `docker-compose.yml` le volume porte maintenant un **nom fixe** (`name: boleryos-data`) : avant, Docker le préfixait du nom de la pile Portainer, et recréer la pile sous un autre nom ouvrait un volume vide (données « effacées »). Si le volume n'existe pas sous ce nom, Docker le crée vide : les anciennes données restent dans l'ancien volume (souvent `<nom-de-pile>_boleryos-data`), à recopier à la main. Le `Dockerfile` déclare aussi `/data` comme volume. Si `/data` n'est **pas** un volume monté (conteneur lancé sans `-v`), un **bandeau jaune** s'affiche en haut de l'Accueil : les données seraient perdues à la prochaine mise à jour. Le bandeau s'affiche aussi pour un **volume anonyme** (conteneur lancé sans volume nommé : Docker en crée un nouveau, vide, à chaque redéploiement). Sous le tableau des instances, l'Accueil indique le **nom du volume** et sa **date de création** : si cette date change après une mise à jour, le volume a été remplacé par un volume vide.

## Fonctionnalités et interrupteur général (Réglages › Fonctionnalités)

- **Bot : ON / OFF** (en haut de chaque page) : à OFF, aucune fonctionnalité ne tourne ; le bot reste pourtant connecté et scanne les planètes. Il repasse **toujours à OFF** après un redémarrage.
- Chaque fonctionnalité a son interrupteur et son **minuteur** : après chaque passage, le bot attend une durée tirée au hasard entre le minimum et le maximum (le minuteur redémarre à la **fin** du passage). On ne peut pas activer sans minuteur. À l'activation (bot sur ON), le premier passage a lieu tout de suite. Pour les Explorations, le minuteur s'appelle « Vague d'explorations toutes les X à Y minutes ». Exceptions : **Fouilles** et **Piratage** n'ont pas de minuteur — ils se relancent tout seuls à la fin de chaque mission, plus le délai choisi dans leur onglet, avec une vérification de secours toutes les 30 minutes (réglable, ou désactivable, pour les Fouilles : voir leur onglet).
- **Un seul passage à la fois.** Si plusieurs sont dues, la plus haute de la liste de priorités passe d'abord ; un passage commencé n'est jamais interrompu (même si le bot passe à OFF) ; quelques secondes séparent deux passages.
- Un passage est repoussé tant que le bot n'est pas dans une partie ou que le contrôle manuel est actif.
- Activations, minuteurs et priorités sont enregistrés dans `/data/features.json` et survivent au redémarrage.
- **« Constructions de bâtiments »** (réglée dans l'onglet Constructions) : à chaque passage, pour chaque planète visée, le bot prend la **première ligne** de la liste dont le niveau actuel est sous le niveau cible et dont le bouton « Améliorer » est actif (mode **« Dès que les ressources suffisent »**, par défaut ; voir **Modes de lancement** plus bas), **clique une fois** (dépense de vraies ressources) et vérifie que le stock a baissé. Une ligne dont le niveau cible est atteint (sur **toutes** les planètes visées) est **retirée automatiquement** de la liste ; il en va de même pour les recherches et pour les lignes de population qui ne se répètent pas (« une seule fois », « effectif à atteindre »), jamais pour celles « à chaque passage ». Au plus **une construction par planète et par passage** ; le même bâtiment n'est pas recliqué avant la fin présumée de sa construction (durée lue sur la carte, +10 %) ; le contrôle manuel l'interrompt ; après **deux lancements de suite dont le débit n'est pas constaté**, la fonctionnalité se désactive. **Tableau « Niveaux actuels »** : au début de chaque passage, le bot lit **une seule page** du jeu, **Empire › Inventaire** (lecture seule, la ligne « Ordre d'affichage » n'est jamais touchée), et en tire le niveau des 16 bâtiments de chaque planète ; le bouton « Relever maintenant » refait ce relevé à la demande (le bot doit être dans une partie et libre). Les colonnes sont retrouvées par nom de planète, pas par position. Case jaune : sous le niveau cible de la liste ; verte : atteint. Le dernier relevé est gardé dans `/data/inventory.json` ; un relevé qui échoue est signalé sans arrêter les constructions. **Niveaux des recherches** : la même lecture d'Empire › Inventaire donne aussi le niveau de chaque recherche (colonne « Total » des lignes « Technologies », commune à l'empire) ; l'onglet Recherches l'affiche dans « Niveaux actuels », avec un bouton **+1** qui ajoute la recherche à la liste d'objectifs au niveau actuel + 1 (désactivé si elle y est déjà ou si son niveau est inconnu) : c'est la seule façon d'ajouter une recherche, il n'y a plus de liste déroulante. Le tableau est affiché en entier, sans barre de défilement, et un clic sur la ligne « Civil » ou « Militaire » masque ou réaffiche ses recherches (choix retenu par le navigateur). Le passage de recherche relève aussi l'inventaire avant de lancer (un échec n'empêche pas le lancement). **Objectifs par planète** : le tableau « Niveaux actuels » est le seul moyen d'ajouter un objectif. Le bouton **+1** d'une case ajoute (ou monte) l'objectif de **cette planète** à niveau actuel + 1 (un clic de plus : +1 encore) ; le **+1** en début de ligne fait de même sur chaque planète, chacune depuis son propre niveau. La liste est **affichée par planète** (un titre par planète, dans l'ordre du scan ; les anciennes lignes « toutes les planètes » en tête) ; ↑ et ↓ déplacent une ligne au sein de sa planète, l'ordre enregistré restant celui que le bot suit. Une ligne de la liste peut donc porter une **planète** (une ligne par bâtiment et par planète, 500 lignes au plus) ; la ligne d'une planète l'emporte sur une ancienne ligne « toutes les planètes » du même bâtiment, et une ligne propre à une planète est retirée dès qu'elle est atteinte sur sa planète. Le choix « Planètes » ne concerne plus que les anciennes lignes « toutes les planètes » (elles continuent de fonctionner telles quelles). Le tableau est affiché en entier et un clic sur « Industrie » / « Infrastructures » masque ou réaffiche ses bâtiments. **Modes de lancement et planètes repliables** : au titre de chaque planète de la liste, un **menu** choisit le mode de cette planète (enregistré dans `/data/constructions.json`, clé `modes`, absente tant que rien n'est choisi). **« Dès que les ressources suffisent »** (par défaut, comportement d'avant) : le bot lance la première ligne que la planète peut payer, et passe aux suivantes si une ligne est trop chère. **« Ordre de la liste »** : si la première ligne encore à faire n'est pas payable, le bot **n'en lance aucune autre** et attend ses ressources (le transport de ressources, s'il est activé, complète cette ligne) ; une ligne bloquée par une autre raison (énergie…) bloque donc aussi la planète. Le mode du titre « Toutes les planètes » vaut pour les planètes qui n'ont pas de mode à elles. Un clic sur le titre d'une planète **masque ou réaffiche ses lignes** (choix retenu par le navigateur) ; le bot suit la liste enregistrée, qu'elle soit masquée ou non. **Planètes sautées** : si le relevé du passage montre que, sur une planète, **toutes** les lignes de la liste sont déjà au niveau cible, le bot ne la visite pas (elle compte comme atteinte pour retirer la ligne) ; planète absente du relevé, bâtiment non lu ou relevé en échec : elle est visitée comme avant, jamais de décision sur de vieilles données. **Effectifs de population** : la même lecture d'Empire › Inventaire (section « Unités terrestres ») donne le nombre de chaque population recrutable sur chaque planète ; l'onglet Population l'affiche dans « Effectifs actuels » et c'est la seule façon d'ajouter une ligne (plus de liste déroulante). Au-dessus du tableau : trois choix pour les boutons — **Max**, **Quantité définie** (N unités) ou **Nombre à atteindre** (N) — avec le champ N, et un interrupteur **À chaque passage de la boucle / Une seule fois** (un effectif à atteindre ne se répète jamais). Le bouton d'une case crée la ligne de **cette planète** (ou remplace la sienne, à sa place dans la liste) ; celui du début de ligne le fait sur chaque planète. Une case jaune est sous son effectif voulu, une verte l'a atteint ; sous le nombre, « MAX » ou « +N » avec ↻ (à chaque passage) ou 1× (une seule fois) rappelle une ligne de recrutement. La ligne la plus précise (une planète, puis quelques planètes, puis toutes) l'emporte pour une même population, quel que soit leur ordre ; 500 lignes au plus. Le tableau est affiché en entier, sans barre de défilement, et un clic sur « Assaut », « Logistique » ou « Administration » masque ou réaffiche ses populations. Le passage de recrutement relève l'inventaire en début de passage : une planète dont tous les objectifs sont des effectifs déjà atteints n'est pas visitée (leur ligne est retirée comme avant) ; si le relevé échoue, toutes les planètes sont visitées. **Non vérifié sur le vrai jeu** : tout a été testé sur un faux jeu reconstitué d'après les pages lues le 06/11 ; commencez par une seule planète et une seule ligne, en regardant la page Écran. **Transport des ressources manquantes** (option de l'onglet Constructions, désactivée par défaut, fichier `/data/transport.json`) : quand une construction de la liste est grisée parce qu'il manque du Fer, du Cristal ou de l'Éther, le bot envoie **ce qui manque à cet instant** (coût de la carte − stock de la planète, plus la **marge**, réglable de 0 à 50 % par pas de 0,5 %, plus 1 000 unités d'avance car l'en-tête du jeu arrondit les stocks) depuis les **planètes donneuses** cochées, dans l'ordre où elles ont été cochées, par **Opérations › Transport**. Voie **fixe** au choix : **Piliers** (arrivée immédiate : la construction est retentée tout de suite) ou **Flotte** (spatial : prend une place de mission ; le bot lit le « Temps de trajet » affiché par le jeu avant de lancer et n'envoie plus rien vers la même planète pendant ce temps de vol **plus un délai aléatoire de 30 s à 5 min** (simulation humaine) ; temps illisible : 30 minutes comptées à la place). Les **modèles** sont ceux du jeu, relevés comme pour les explorations (bouton « Relever les modèles »), essayés dans l'ordre jusqu'à un lancement possible. Si la voie est « Piliers » et que les Piliers d'une donneuse sont **fermés** (état lu dans « Gérer les Piliers », ou lancement grisé), le bot essaie en **spatial** avec les **modèles Flotte de secours** ; sans modèle de secours, ou si le spatial est impossible, la donneuse est **sautée** (dit au journal). Une donneuse n'envoie que ce qu'elle a (pas de réserve gardée) ; la suivante complète. La cible est choisie par un clic dans la liste « Vos colonies » du jeu. Le débit de la donneuse est vérifié ; après **deux envois de suite non confirmés**, l'option se désactive. Le bot ne touche jamais à « Mobilisation générale », « Réinitialiser » ni aux boutons de Piliers. Les noms des champs et des boutons (`Cargaison : Fer`, `#raid-launch-btn`, `#pillars-launch-btn`) viennent d'un relevé du vrai jeu (Asterion, 23/11) ; **aucun envoi n'a encore été lancé par le bot sur le vrai jeu**.
- **Confirmation « production longue »** (Population, Composants, Assemblages, Appareils spécialisés) : quand la file dépasse environ 1 jour, le jeu n'envoie pas la commande après le clic sur « Recruter » / « Produire » / « Lancer » : il affiche **un encart dans la page** (relevé sur le vrai jeu le 26/11 : titre « Production longue », « Ce pack de production dure 1 j 10 h. Confirmez-vous son lancement ? », boutons ANNULER et CONFIRMER). Avant, le bot ne le voyait pas : rien n'était lancé alors qu'il croyait l'avoir fait. Maintenant, juste après son clic de lancement, le bot attend jusqu'à 2,5 s cet encart ; s'il apparaît, il clique sur **CONFIRMER** (la ligne réglée fait foi : la file longue est voulue) et écrit le texte du jeu dans le journal (« Le jeu demande une confirmation avant le lancement : … — confirmée. »). Il ne clique jamais sur ANNULER. Une vraie fenêtre native du navigateur (confirmer / alerte) est aussi acceptée pendant ce clic ; saisie et « quitter la page » restent refusées. Code : `app/dialogs.py`. **À confirmer sur le vrai jeu** : le clic sur CONFIRMER (non encore validé) ; les constructions et recherches ne sont pas concernées.
- **« Assemblages de vaisseaux »** et **« Production de composants »** (Chantier spatial, onglets Assemblages et Composants) : le bot lit la page `/shipyard`. Les **modèles de vaisseaux** sont lus par un **scan** (une fois par connexion, après le scan des planètes, et à la demande avec le bouton « Scanner les modèles ») car ils se créent dans le jeu à tout moment. Pour chaque planète visée (toutes, une seule ou plusieurs), le bot applique la première ligne de chaque élément : le vaisseau est d'abord remis en mode **Construction** (ressources, jamais « Assemblages »), puis le bot clique sur MAX pour connaître le maximum payable, saisit `min(voulu, payable)` et clique sur « Lancer » (ou « Produire » pour un composant) ; il vérifie ensuite le débit des ressources. Pour « effectif à atteindre », les unités déjà commandées mais pas encore terminées sont comptées. Avant chaque planète, le bot vérifie que la page affiche bien les chiffres de la nouvelle planète. Validé sur le vrai jeu le 07/11 (un >Lentus et un Chasseur lancés par le bot). **Tableau « Effectifs actuels » des composants** : Empire › Inventaire ne liste pas les composants ; l'effectif (« ×N » de chaque ligne) vient de l'onglet Composants du Chantier spatial, que le bot lit pour chaque planète au début de son passage (avant de produire) ; le bouton « Relever maintenant » visite chaque planète du scan et relit cet onglet sans rien produire (le bot doit être dans une partie et libre). Le dernier relevé est gardé dans `/data/component_counts.json` ; un composant jamais relevé sur une planète s'affiche « — ». Les boutons du tableau créent des lignes comme pour la population (une ligne par composant et par planète, la plus précise l'emporte sur une ligne « toutes les planètes », 500 lignes au plus) ; contrairement aux constructions, le bot ne saute pas une planète dont tous les objectifs sont atteints.
- **« Explorations »** (onglet Exploration, une seule configuration) : moyen **Piliers ou Flotte**, composition par **modèle du jeu** ou **quantité par unité**, **copies** (1 à 10) et **durée** (1 à 6 h), planètes toutes / une / plusieurs, rythme **nombre fixe par planète et par passage** ou **autant que possible**. **Une fois par jour** (et avec le bouton « Refaire le relevé du jour »), le bot relève pour chaque planète la **brèche la plus proche** — il recentre la Galaxie sur la planète, dézoome jusqu'à voir une brèche et **lit les positions réelles** que la carte reçoit du serveur (aucune requête ajoutée) ; en secours seulement, il classe les brèches listées par une formule tirée des adresses — ainsi que les **modèles** Piliers et Flotte. À chaque passage, il lit les compteurs **« Explorations quotidiennes »** et **« Explorations actives »** (communs au compte) et ne lance rien si le quota ou les places sont épuisés ; une planète à qui il manque des unités, de l'énergie ou de la Trame est **sautée** et la suivante est servie. Le lancement est confirmé par la hausse du compteur quotidien. Le bot ne touche jamais à « Supprimer » (modèle), au rappel d'une flotte d'exploration, à « Mobilisation générale » ni aux boutons de champ de force et de piliers. Validée sur le vrai jeu le 07/11 (1 exploration lancée par le bot depuis Egide).
- **« Fouilles »** (onglet Fouilles) : une **ligne** par planète de départ et par durée — **équipe** choisie unité par unité (Soldat, Rempart de Fer, Spectre du Rift, Surchargeur Plasmique, Faucheur Cinétique, Scientifique, Mineur ; **1 à 5 000 unités**), **durée** 3, 6, 12 ou 24 h, **nombre de places**, et **Mira Venn** sur une seule ligne (partie sans héros si elle est déjà en mission). Le joueur choisit un **délai avant relance** (minimum et maximum en minutes). On peut **régler plus de Fouilles que le jeu n'en permet** (maximum « Fouilles actives », 6 sur Asterion) ou que la planète n'a de sites libres : le bot traite les planètes dans l'ordre, lance sur chacune autant de Fouilles que d'emplacements trouvés, saute une planète sans site et s'arrête quand le jeu est plein ; le reste attend une place libre (les Fouilles en trop ne réservent pas de places de mission). Un **coût maximum en RT par Fouille** (facultatif) est un garde-fou : le bot lit la ligne « RT requis » avant de cliquer (format réel du jeu : « 0,077 RT », virgule décimale et « RT » collé) et ne lance pas la Fouille si le coût est supérieur au maximum ou illisible. Le coût réel étant fractionnaire, le maximum accepte les **décimales** (« 0,5 » ou « 0.5 ») et la comparaison se fait sans arrondi. **Une fois par jour** (et avec « Refaire le relevé du jour »), le bot relève les **emplacements libres les plus proches** de chaque planète de départ (positions réelles de la carte ; le jeu ne livre que 25 objets par réponse, les emplacements libres en dernier : si la première page n'en montre aucun, le bot descend la liste « Vue d'ensemble » pour charger les portions suivantes ; formule des adresses en secours). Le journal indique le nombre d'objets lus, le total annoncé et les planètes libres annoncées par le jeu ; si le jeu en annonce mais que le bot n'en lit aucune, l'échec le dit et le nombre maximum de Fouilles actives. À chaque passage, il lit les Fouilles dans « Missions en cours » (fin réelle, retards compris, Fouilles lancées à la main adoptées par leur ligne) ; une place se libère à la **fin de sa Fouille plus un délai tiré au hasard** entre le minimum et le maximum, et la Fouille suivante part vers le site libre le plus proche **sans Fouille en cours**. **Avant chaque lancement**, le bot **relève de nouveau les emplacements libres** de la planète sur la carte (le relevé du jour peut être périmé) et ne lance que sur une position réellement disponible ; si le relevé échoue ou ne montre aucune position libre, la planète est sautée avec la raison au journal (relevé du jour et lancement) — **non vérifié sur le vrai jeu**. Il respecte « Fouilles actives » et « Missions actives », et confirme chaque lancement par la hausse du compteur. **Vérification de secours** (réglable dans l'onglet, 30 minutes par défaut, de 1 à 1 440 min) : même sans place attendue, le bot repasse au plus tard à ce délai pour relire « Missions en cours » (Fouilles lancées à la main, retards) ; la décocher le fait repasser seulement à l'heure où une place se libère ; le dernier délai choisi est mémorisé avec les réglages et revient en recochant la case, même après un rechargement de la page ; un délai illisible ou hors plage est refusé à l'enregistrement (30 minutes quand aucune Fouille n'est suivie, pour ne jamais s'arrêter définitivement) ; le nouveau délai compte à partir du prochain passage ; réglage `recheck_min` de `excavations.json` (0 = désactivée, absent = 30). Une Fouille **ne peut pas être rappelée**. **Pas encore lancée par le bot sur le vrai jeu** (lancement manuel observé le 07/11).
- **« Piratage (expérience de Naël) »** (onglet Piratage) : réglages **planète de départ** et **délai avant relance** (minimum et maximum en minutes, choisis par le joueur). But : faire gagner de l'expérience à **Naël Soryn**. Une fois par jour, le bot relève les **Errants les plus proches** de la planète (positions réelles de la carte) en gardant ceux dont le bouton Drone n'est pas grisé (ratio ×2). À chaque passage, il lit « Missions en cours » et l'état de Naël ; dès que le piratage précédent (30 minutes) est fini **et** que le délai tiré au hasard est écoulé, il pirate de nouveau **le même Errant**. Si le jeu refuse cet Errant (piliers désactivés…), le suivant le plus proche devient la cible. Un piratage ne s'annule pas et l'Errant est prévenu ; les rapports ne sont pas lus. **Pas encore lancé par le bot sur le vrai jeu** (lancement manuel observé le 07/11).
- **« Forages de planètes minières »** (onglet Forages, relance automatique) : planètes de départ, ressources visées (Fer, Cristal, Éther), nombre de Mineurs par forage (1 Foreuse orbitale + 1 à 200 000 Mineurs), nombre de places, délai avant relance. Le bot lit la ressource de chaque planète minière dans les données de la carte, vise la plus proche de la bonne ressource sans forage en cours (jamais deux forages sur la même) et lance par Opérations › Flotte › Forage. Il suit les trois phases dans « Missions en cours » (aller, extraction — sans heure de fin —, retour) ; la flotte revient seule (soute pleine ou planète épuisée) ; la place est relancée au retour plus le délai, sur la même planète minière si elle existe encore, sinon sur une nouvelle. Les forages de plusieurs jours sont retrouvés après un redémarrage. Le bot ne rappelle jamais un forage (seule la fonctionnalité « Retours de flottes » rappelle d'autres flottes).
- **« Dons de jetons d'alliance »** (onglet Alliance + minuteur « Donner des jetons toutes les X à Y minutes ») : à chaque passage, le bot ouvre Alliance › Techs et donne **tous** ses jetons, **1** ou **2** (au choix) à la technologie marquée « priorité de dons de l'alliance », et à aucune autre ; il ne change jamais la priorité. La priorité est reconnue aussi pour un membre **sans droits de chef d'alliance** (icône « X est la priorité de dons de l'alliance », relevée sur Kael le 26/11 ; don lui-même non encore vérifié sur ce serveur), et le bot attend jusqu'à 6 s que la page l'affiche avant de conclure qu'il n'y en a pas. Le don est confirmé par la baisse du compteur de jetons (un jeton revient environ toutes les 2 h, 6 au plus).
- **« Retours de flottes »** (onglet Flottes, relance automatique) : le bouton **« Relever les flottes en vol »** ouvre les **Capteurs** du jeu (lecture seule) et liste chaque mouvement : contenu, départ, destination, temps restant. Pour une flotte rappelable, on choisit la **date et l'heure où elle doit être rentrée** (heure de Paris, à la seconde) et on la programme ; la **marge d'avance** du clic (5 s par défaut, 0 à 120 s) est réglable. Le jeu ne donne la durée du retour qu'au moment du rappel : à chaque contrôle, le bot ouvre « Préparer le retour de la flotte » et **lit l'heure affichée** (vrai jeu : « Si vous confirmez maintenant, la flotte reviendra le JJ/MM/AAAA HH:MM:SS ») : c'est l'arrivée prévue si on rappelle maintenant. Trop tôt, il referme la fenêtre et programme le contrôle suivant (environ 1 min avant le clic estimé ; la liste affiche « clic prévu vers le JJ/MM à HH:MM:SS » puis « prochain contrôle du bot le … » : le clic prévu est une estimation, elle se précise à chaque contrôle) (l'arrivée prévue n'avance jamais de plus de 2 s par seconde, donc il ne dépasse jamais l'heure) ; à moins d'environ 90 s, il reste dans la fenêtre, amène la souris sur « Confirmer le retour », relit l'heure deux fois par seconde et **confirme le rappel** quand l'arrivée prévue + la marge (+ 3 s d'avance pour le délai du clic) atteint l'heure voulue. Dès qu'un retour est programmé, la fonctionnalité est **réveillée tout de suite** (sans attendre son prochain passage, jusqu'à 30 min). Vérification après le clic : la flotte ne doit plus être rappelable sur son trajet (c'est l'état réel de la flotte qui fait foi, pas la fermeture de la fenêtre : sur le vrai jeu, la fenêtre peut rester affichée alors que le rappel est pris en compte). Sont refusés avec une explication : heure déjà trop proche (« trop tard », avec l'arrivée la plus tôt possible), flotte rentrée entre-temps, durée de retour illisible, bouton de confirmation non reconnu (le bot ne devine jamais un bouton) ; une heure dépassée de plus de 2 min est abandonnée. Les retours programmés sont gardés dans `fleets.json` et survivent à un redémarrage. **Jamais** les flottes d'exploration, de fouille, de forage, de piratage et d'espionnage (masquées). **Vérifié sur le vrai jeu (23/11)** : le relevé (1 flotte lue), le texte de la fenêtre de retour, le réveil immédiat et le clic de confirmation (un rappel réel accepté par le jeu, la fenêtre restant ouverte) ; **non vérifié** : l'attente de plusieurs minutes avant le clic (précision à l'heure voulue), et si l'heure de la fenêtre se met à jour en direct. Premier essai conseillé : une seule flotte, une heure lointaine, en regardant la page Écran.
- **Missions** (automatique, sans réglage) : **une fois par jour** (date française), le bot ouvre l'onglet Missions et clique sur chaque « Récupérer » (missions quotidiennes, hebdomadaires et mensuelles atteintes ; les onglets Quêtes et Événements ne sont pas touchés). Cela se fait (A) quand vous mettez le bot sur **OFF** — après le passage en cours — et (B) quand le **planning** termine la **dernière plage de la journée**, juste avant la déconnexion. Le résultat est noté dans le journal.
- **Planning** (onglet Planning) : plages horaires actives pour chaque jour de la semaine (heure française), plusieurs par jour, une plage pouvant passer minuit ; décalage aléatoire de X à Y minutes, avant ou après, au début et à la fin de chaque plage. Le bouton ON/OFF reste le maître : sur **ON** avec « Utiliser le planning », le bot n'agit que pendant une plage ; en dehors, le passage en cours se termine, puis le bot **ferme la page du jeu en gardant la session** (comme un onglet fermé, sans « Déconnexion ») et ne fait rien jusqu'à la plage suivante, où il rouvre le jeu et retrouve la partie (connexion avec les identifiants seulement si le jeu a expiré la session). Un jour sans plage est inactif. Sur OFF, en contrôle manuel ou pendant une campagne d'espionnage (manuelle), le planning ne s'applique pas.
  **Fonctionner hors planning :** chaque fonctionnalité a, sous son titre (liste Fonctionnalités et en-tête de sa page), une case qui la dispense du planning général. Tant qu'au moins une fonctionnalité **activée** a cette case cochée, le bot **garde la page du jeu ouverte** hors plage et **seules** ces fonctionnalités travaillent ; les autres restent en pause jusqu'à la plage suivante. Les horaires propres du Piratage et de l'Exploration restent respectés, et leurs plages peuvent alors sortir du planning général. Décochée (par défaut) : comportement habituel. Réglage enregistré dans `features.json` (clé `ignore_planning`).
- **Bonus d'activité** (automatique, sans réglage) : au début de chaque passage d'une fonctionnalité, de la campagne d'espionnage et des relevés manuels, le bot regarde si le bouton « Bonus » (en bas à gauche) est affiché — il n'apparaît que lorsqu'un gain est disponible, toutes les 2 à 4 h — et clique dessus, quelle que soit la planète active (qui reçoit les ressources). Le message du jeu (« Bonus récupéré … ») est noté dans le journal.
- **Espionnage des Errants** (onglet Espionnage, **manuel**, hors de l'ordonnanceur) : réglages **planète**, **minimum de Fer, Cristal et Éther**, et **nombre de ressources (1, 2 ou 3)** qui doivent atteindre leur minimum. Le bouton « Lancer l'espionnage » met le bot sur **OFF** (les autres automatismes restent arrêtés jusqu'à ce que vous les relanciez), ouvre la Galaxie centrée sur la planète au **zoom ×17,5**, charge toute la liste « Fenêtre visible » (« Afficher la suite ») et clique sur **Drone** pour chaque planète d'Errant **[AI]** (un Drone grisé = Drone indisponible, Errant hors du ratio ×2 de points, sauté). Un rapport est **gardé** (« Fermer le message ») si assez de ressources atteignent leur minimum, sinon **supprimé** (« Supprimer le message ») ; un rapport illisible est gardé. Les Errants dont les **piliers sont désactivés** vont dans la liste « Piliers fermés », vidée à chaque lancement. Trois refus de suite pour une autre raison arrêtent la campagne. L'écran n'affiche que le **nombre de cibles retenues**. **Pas encore lancée par le bot sur le vrai jeu.**
- La fonctionnalité « Test (ne fait rien) » n'agit pas dans le jeu : elle sert à vérifier minuteurs et priorités, et sera retirée quand la première vraie fonctionnalité arrivera.

## Données du joueur

- Aucun identifiant ni mot de passe dans l'image Docker, `docker-compose.yml`, les variables d'environnement ou un volume.
- Ils sont envoyés par l'interface, utilisés une fois pour remplir le formulaire du jeu, puis oubliés. Seule la session du navigateur (cookies) reste en mémoire, jusqu'à la déconnexion ou l'arrêt du conteneur.
- Le journal ne contient jamais le mot de passe, et l'identifiant y est masqué (`jo***`).

## Lancer

**Avec Portainer (Web editor)** : Stacks > Add stack > Web editor, coller le contenu de `docker-compose.yml`, puis Deploy. Aucune variable à déclarer.

L'image `ghcr.io/kamegrazi56/boleryos:latest` est construite et publiée automatiquement par GitHub Actions (`.github/workflows/docker-publish.yml`) à chaque mise à jour du code. Pour mettre à jour le bot : attendre la fin du workflow dans l'onglet Actions du dépôt, puis redéployer la stack dans Portainer (`pull_policy: always` télécharge la dernière image).

Première publication : le paquet est créé en privé. Sur GitHub, aller dans le profil > Packages > `boleryos` > Package settings > Change visibility > Public, pour que Portainer puisse le télécharger sans identifiants.

**Avec Docker en ligne de commande** :

```bash
docker compose up --build
```

Puis ouvrir `http://<adresse-du-serveur>:7654`. Le port se change dans `docker-compose.yml` (`"7654:8000"` : port du serveur à gauche, port du conteneur à droite).

**Attention** : l'interface reçoit le mot de passe du jeu et n'est accessible qu'en HTTP. Ne l'exposez pas sur internet sans protection (réglages `ui_user` / `ui_password` ci-dessous, et idéalement un reverse proxy HTTPS).

## Réglages

Ils se modifient directement dans `app/config.py` (aucune donnée de joueur) :

| Champ | Rôle | Défaut |
|---|---|---|
| `login_url` | Page contenant le formulaire de connexion (URL de test de l'éditeur possible) | `https://aleryos.com/fr` |
| `ui_user` / `ui_password` | Protège l'interface du bot par mot de passe (HTTP Basic) | désactivé |
| `human_mode` | Comportement humain : pauses courtes et aléatoires entre les actions, souris déplacée progressivement, frappe touche par touche | `True` |
| `human_delay_min` / `human_delay_max` | Pause entre deux actions (secondes) | `0.4` / `1.4` |
| `key_delay_min` / `key_delay_max` | Délai entre deux touches (secondes) | `0.05` / `0.18` |
| `show_cursor` | Point rouge à l'endroit de la souris dans la vue en direct | `True` |
| `screenshot_interval` | Intervalle entre deux images de la vue en direct (secondes) | `0.4` |
| `login_timeout` | Attente maximale du résultat de la connexion, en secondes | `30` |
| `max_instances` (`MAX_INSTANCES`) | Nombre maximal d'instances de jeu | `5` |
| `autostart` (`AUTOSTART`) | Les instances qui tournaient reprennent au démarrage de l'application (`AUTOSTART=0` pour l'éviter) | `True` au lancement ; `False` dans les tests |
| `email_selector`, `password_selector`, `submit_selector` | Sélecteurs du formulaire | relevés sur le site |

Les mêmes réglages peuvent aussi être surchargés par variables d'environnement (`DATA_DIR`, `LOGIN_URL`, `UI_USER`, `UI_PASSWORD`, `LOGIN_TIMEOUT`, `EMAIL_SELECTOR`, `PASSWORD_SELECTOR`, `SUBMIT_SELECTOR`), mais ce n'est pas nécessaire.

Ne mettez jamais un mot de passe réel dans `app/config.py` si le dépôt est public.

## Connexion et Cloudflare Turnstile

Le site protège la connexion avec Cloudflare Turnstile. Le bot **ne résout pas** de captcha. Pour tester les actions du jeu, utiliser un environnement de test fourni par l'éditeur (`LOGIN_URL` ou règle d'exception). Si Turnstile bloque, le journal l'indique et la page Écran montre l'écran bloquant (le navigateur reste ouvert après un échec).

La connexion est considérée comme réussie quand le champ mot de passe disparaît ; l'échec est détecté via un élément `role="alert"` ou un délai dépassé. Ces critères sont à affiner en observant la vraie page après connexion.

## Moteur de lecture (Réglages › Compte et univers)
Chaque instance a son moteur :
- **Navigateur** (par défaut) : le bot lit chaque page du jeu et clique dessus, dans Chromium.
- **Hybride** : il lit l'état du jeu directement par l'API de l'univers (planètes, modèles, bâtiments, effectifs), sans ouvrir de page, avec la session du navigateur ; les niveaux de recherche et toutes les **actions** restent dans Chromium. Si l'API ne répond pas, la lecture retombe sur le navigateur et le journal le dit.
- **API seule** (diagnostic, choisie par l'API `PUT /api/preferences`, pas dans l'interface) : lecture seule, aucune fonctionnalité d'action.

**Pourquoi pas d'actions par l'API :** le serveur du jeu refuse (HTTP 403, Cloudflare) la connexion WebSocket d'un client qui n'est pas son navigateur ; ce refus est respecté, pas contourné. Chromium reste donc nécessaire : le gain de mémoire est limité (plus de page de lecture à ouvrir), pas de retrait de Chromium. Détails : [`docs/API-PROTOCOL.md`](docs/API-PROTOCOL.md).
